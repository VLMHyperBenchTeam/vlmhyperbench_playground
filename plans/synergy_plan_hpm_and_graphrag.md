# Синергия проектов: HPM (Environment Layer) и GraphRAG (Knowledge Layer)

Этот план описывает, как два параллельных проекта могут переиспользовать наработки друг друга для ускорения реализации и достижения "лучшего из двух миров".

## 1. Точки пересечения

### 1.1. HPM для GraphRAG
Проекту GraphRAG (Git + Graph + RAG) нужен механизм управления окружением, который:
*   Динамически подгружает нужные парсеры (Tree-sitter для разных языков).
*   Управляет версиями бэкендов (Neo4j vs FalkorDB).
*   Позволяет работать в режиме "библиотеки поверх текущего venv", не требуя Docker.

### 1.2. GraphRAG для VLMHyperBench
Нашему проекту (VLMHyperBench) нужен Memory Bank, который:
*   Понимает структуру HPM плагинов.
*   Связывает ADR (документацию) с реализацией.
*   Позволяет агенту быстро ориентироваться в графе вызовов при рефакторинге.

## 2. Поэтапная стратегия реализации

### Этап 1: "HPM Lite" и Структурный Граф (Shared Foundation)
*   **HPM:** Реализуем "библиотечную" часть HPM, которая умеет парсить `hpm.yaml` и вызывать `uv pip install -e` для локальных путей. Это позволит GraphRAG проекту использовать HPM для управления своими плагинами-парсерами.
*   **Graph:** Реализуем базовый индексатор (на базе `ast` и `tree-sitter`), который строит граф **структуры** (File -> Class -> Function). Это общая часть для обоих проектов.

### Этап 2: "Memory Bank" и "Git-Aware Indexing"
*   **VLMHyperBench:** Добавляем в граф слой документации (ADR, планы). Связываем `Requirement` -> `Function`. Это превращает структурный граф в Memory Bank.
*   **GraphRAG Project:** Добавляем слой Git (Commit -> File). Реализуем инкрементальную индексацию по diff.

### Этап 3: Полная интеграция
*   **VLMHyperBench:** Использует Git-слой из второго проекта, чтобы понимать "почему этот код изменился" (связь коммита с задачей).
*   **GraphRAG Project:** Использует HPM для полной изоляции воркеров-индексаторов в Docker (если нужно масштабироваться на огромные репозитории).

## 3. Разделение Memory Bank и Graph Tool

Чтобы не дублировать код и эффективно использовать инструменты, предлагается следующее разделение в MCP:

### Вариант: Единый MCP Сервер с разными инструментами (Namespace)
Я рекомендую использовать **Neo4j** как единое хранилище, но разделить логику доступа:

1.  **Tool: `query_code_structure` (Graph)**
    *   **Цель:** Ориентация в коде.
    *   **Запросы:** "Кто вызывает эту функцию?", "Какая иерархия классов?".
    *   **Схема:** AST-based (Files, Classes, Methods).

2.  **Tool: `query_memory_bank` (Memory)**
    *   **Цель:** Понимание контекста и истории.
    *   **Запросы:** "Почему мы выбрали этот подход?", "Какие были требования к этой фиче?".
    *   **Схема:** ADR, Requirements, Decisions + связи с кодом.

### Почему это лучше?
*   **Одна БД:** Вы можете в одном Cypher-запросе спросить: `MATCH (d:Decision)-[:AFFECTS]->(f:Function) WHERE f.name = "process" RETURN d.text`.
*   **Разный контекст:** Агент может вызывать только `query_code_structure`, когда он просто пишет код, экономя токены на чтении документации.

## 4. Ближайшие шаги (Action Items)

1.  **Для HPM:** Выделить логику разрешения путей и установки через `uv` в отдельный модуль, не привязанный к Docker Entrypoint.
2.  **Для Графа:** Создать базовую онтологию (Schema), которая будет поддерживать и HPM-сущности (пакеты), и стандартные Python-сущности.
3.  **Для Агента:** Настроить MCP сервер Neo4j, который будет общим интерфейсом к этой базе.
