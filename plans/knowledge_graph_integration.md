# Концепция интеграции Графа Знаний (Knowledge Graph) в VLMHyperBench

**Ответ на вопрос:** Да, граф взаимосвязей был бы **чрезвычайно полезен** и для меня (как агента), и для проекта в целом.

Учитывая сложность VLMHyperBench (микросервисная архитектура, динамические плагины HPM, Docker-контейнеры), плоский список файлов или даже поиск по коду (RAG) не дают полной картины. Граф знаний позволит переходить от "поиска текста" к "пониманию структуры".

## 1. Почему это полезно для Агента (Memory Bank)

### 1.1. Навигация по зависимостям HPM
В текущей задаче (HPM) мы создаем систему динамических зависимостей.
*   **Проблема:** Чтобы понять, какие адаптеры сломаются при обновлении `api_wrapper`, мне нужно грепать все `hpm.yaml` и код.
*   **Решение с Графом:** Запрос `MATCH (p:Package)-[:DEPENDS_ON]->(lib:Package {name: "api_wrapper"}) RETURN p.name` мгновенно покажет зону поражения.

### 1.2. Связь Архитектуры и Кода
Мы пишем много ADR и планов.
*   **Проблема:** Код со временем расходится с документацией.
*   **Решение:** Связи `(Doc:ADR-002)-[:IMPLEMENTED_BY]->(Code:HPM_Runtime)` позволят мне при изменении кода напоминать: "Это изменение противоречит ADR-002, обновите документацию".

### 1.3. Экономия контекста
Вместо того чтобы читать 50 файлов "на всякий случай", я смогу делать точечные запросы:
"Найди все классы, которые наследуются от `AbstractBackend` и используются в `Orchestrator`".

## 2. Предлагаемая схема графа для VLMHyperBench

Для нашего проекта я предлагаю расширить стандартную схему (File/Class/Function) специфичными сущностями:

### Новые Узлы (Nodes)
*   **`HPM_Package`**: Сущность, описываемая `hpm.yaml`.
    *   Свойства: `name`, `version`, `type` (service/library).
*   **`Service`**: Docker-сервис или компонент системы.
*   **`ADR`**: Архитектурное решение.

### Новые Связи (Relationships)
*   `(:HPM_Package)-[:DECLARES_DEPENDENCY]->(:HPM_Package)`: Зависимость из манифеста.
*   `(:HPM_Package)-[:EXPOSES_ENTRYPOINT]->(:Function)`: Связь entrypoint'а с Python-функцией.
*   `(:Service)-[:USES_IMAGE]->(:DockerImage)`.

## 3. План внедрения (Roadmap)

Если мы решим это внедрять, я предлагаю следующий путь:

1.  **Setup:** Поднять `neo4j` в docker-compose (как описано в вашем плане).
2.  **Indexer Script:** Написать скрипт (Python + `ast`), который:
    *   Парсит `.py` файлы (классы, функции, импорты).
    *   Парсит `hpm.yaml` файлы (пакеты, зависимости).
    *   Парсит Markdown заголовки (документация).
    *   Заливает это в Neo4j.
3.  **Agent Integration:** Использовать MCP сервер для запросов к графу в процессе работы над задачами.
