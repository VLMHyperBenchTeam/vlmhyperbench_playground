# Разделение ответственности: Orchestrator vs HyperPackageManager (hpm)

## 1. Контекст проблемы

В текущей архитектуре VLMHyperBench процессы оркестрации контейнеров и управления зависимостями тесно переплетены. `Orchestrator` не только запускает контейнеры, но и знает слишком много о внутренней структуре пакетов, их источниках и способах установки (JIT). Это нарушает принцип единственной ответственности и усложняет переиспользование логики управления пакетами в других проектах.

Результаты Deep Research подтверждают, что `hpm` должен быть самостоятельным инструментом ("Control Plane" над `uv`), а не просто утилитой внутри бенчмарка.

## 2. Предлагаемое разделение (Architectural Split)

Мы предлагаем четко разделить зоны ответственности на два уровня: **Infrastructure Layer** (Orchestrator) и **Environment Layer** (hpm).

### 2.1. Orchestrator (Infrastructure Layer)
**Роль:** Управление жизненным циклом *контейнеров* и *вычислительных ресурсов*.

**Зона ответственности:**
*   **Scheduling:** Планирование задач (Inference, Eval) на доступные GPU.
*   **Container Lifecycle:** Запуск (`docker run`), мониторинг, остановка контейнеров.
*   **Volumes & Network:** Подключение дисков с данными и настройка сети.
*   **Config Injection:** Проброс переменных окружения (`ENV_VARS`) и секретов.
*   **HPM Invocation:** Оркестратор *делегирует* настройку окружения инструменту `hpm`. Он не знает, *как* устанавливаются пакеты, он просто говорит `hpm`: "Подготовь окружение для задачи X".

**Что Оркестратор перестает делать:**
*   Парсить `package.yaml` реестры напрямую.
*   Формировать команды `pip install ...`.
*   Разрешать конфликты версий зависимостей.
*   Знать разницу между `git`, `pypi` и `local` источниками (это детали `hpm`).

### 2.2. HyperPackageManager (Environment Layer)
**Роль:** Управление *содержимым* Python-окружения внутри (и вне) контейнеров.

**Зона ответственности:**
*   **Manifest Resolution:** Чтение `hpm.yaml`, разрешение графа плагинов.
*   **Source Management:** Выбор источника (`git`/`local`/`pypi`) в зависимости от `RUN_MODE`.
*   **Installation Strategy:** Генерация и исполнение команд установки (`uv pip install`).
*   **Environment Composition:** Сборка "виртуальных пакетов" (например, выбор конкретной реализации `vector-db`).
*   **Locking:** Генерация воспроизводимых `hpm.lock` файлов (snapshotting).

## 3. Точка интеграции: "Bootstrap Protocol"

Взаимодействие между Оркестратором и HPM происходит через стандартизированный протокол запуска (Bootstrap).

### Сценарий: Запуск Инференса

1.  **Orchestrator (Host):**
    *   Читает конфиг запуска (`RunTask`).
    *   Видит требование: `model=qwen2-vl`, `task=vqa`.
    *   Формирует список требуемых *абстрактных* плагинов: `["vlm-adapter-qwen", "metric-vqa"]`.
    *   Запускает Docker-контейнер.
    *   **Команда запуска:**
        ```bash
        hpm run --profile inference --plugins vlm-adapter-qwen,metric-vqa -- python -m vlm_inference.main
        ```
        *(Вместо прямого вызова python или сложного bash-скрипта)*

2.  **HPM (Inside Container):**
    *   Получает управление при старте.
    *   Читает локальный или смонтированный реестр манифестов.
    *   Определяет `RUN_MODE` (из env var).
    *   **JIT Install:**
        *   Если `prod`: качает wheel из PyPI или git tag.
        *   Если `dev`: линкует локальную папку (смонтированную Оркестратором).
    *   Выполняет `uv pip install`.
    *   Передает управление целевому процессу (`python -m vlm_inference.main`).

## 4. Преимущества новой схемы

1.  **Agnostic Orchestrator:** Оркестратор становится проще. Он может запускать любые задачи, не зная деталей их Python-стека.
2.  **Reusable HPM:** `hpm` можно использовать локально без Докера (`hpm run ...`), в CI/CD, или в других проектах.
3.  **Clean Interfaces:** Контракт взаимодействия сужается до CLI-аргументов `hpm`.
4.  **Dev/Prod Parity:** Логика переключения режимов инкапсулирована в `hpm` и работает одинаково везде.

## 5. Управление Реестрами (Registry Governance)

Реестры (`hpm.yaml`, `package.yaml`) являются "источником правды" для композиции системы. Мы принимаем модель управления: **"Human via CLI"**.

### 5.1. Человек (Developer / Architect)
Разработчик взаимодействует с реестром не редактируя YAML-файлы вручную, а через высокоуровневый CLI интерфейс `hpm`.

*   **Регистрация:** `hpm registry add <package-url>` — добавляет новый пакет в реестр.
*   **Обновление:** `hpm registry update <package-name> --tag v1.2.0` — фиксирует версию для продакшена.
*   **Dev Mode:** `hpm dev link <local-path>` — создает оверлей для локальной разработки.

### 5.2. CI/CD (Build Agent)
CI система работает в режиме "Read-Only Consumer". Она никогда не принимает решений об архитектуре, а лишь строго следует инструкциям из манифестов.

*   **Сборка:** Читает `hpm.lock` или `package.yaml`, гарантируя воспроизводимость.
*   **Validation:** Проверяет целостность графа зависимостей перед сборкой.

## 6. Миграционный путь

1.  Выделить код `DependencyInjector` и `RegistryManager` (части, касающиеся пакетов) в отдельную библиотеку `hpm-core`.
2.  Создать CLI-обертку `hpm` с командами `install`, `run`, `scan`.
3.  Заменить прямые вызовы установки в `Orchestrator` на вызовы `hpm install` / `hpm run`.
